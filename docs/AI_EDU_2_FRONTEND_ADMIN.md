# AiEdu 2.0 — клиентская админ-панель

Страница `/admin` реализована в `frontend/src/app/admin/page.tsx`, компоненты и изолированные светлые стили — `frontend/src/components/admin/`. Рабочее пространство сохраняет прежний контракт `/profile`; добавлены отдельное чтение собственных прав и ссылка «Админ-панель» в окне профиля только для активного admin. Никакие рабочие базы, внешние приложения или production credentials при разработке не использовались. Deployment и git push не выполнялись.

## Подключение по шагам

1. Подготовьте отдельный staging Supabase и резервную копию. Сначала примените миграции `20261028000001`–`20261105000004` в порядке имён, если они ещё не применены. Не запускайте повторно уже применённые миграции. Проверьте имеющиеся нестандартные policies/grants по [серверной инструкции](AI_EDU_2_BACKEND_ADMIN.md).
2. Примените **один раз** `supabase/migrations/20261123000005_access_roles_analytics.sql` в SQL Editor выбранного staging-проекта с правами владельца миграций. Альтернатива из корня репозитория с настроенным защищённым DSN владельца staging:

   ```sh
   psql "$STAGING_MIGRATION_DATABASE_URL" -v ON_ERROR_STOP=1 \
     -f supabase/migrations/20261123000005_access_roles_analytics.sql
   ```

   SQL уже содержит BEGIN/COMMIT. Это меняет схему и grants: сначала проверьте на staging. Миграция не выполнялась нами на существующих базах. Runtime backend подключается отдельным серверным логином: владелец выдаёт `GRANT aiedu_backend TO <runtime_login>`. Такой логин не должен владеть таблицами или иметь SUPERUSER/BYPASSRLS/DDL. Группа не предназначена для браузера или преподавателей.
3. На сервере задайте `ENVIRONMENT=staging`, `LOCAL_DEV_USER_ID=` (пусто), `DATABASE_URL` для runtime login, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` из staging. Установите `ANALYTICS_TIMEZONE=Asia/Almaty`: интерфейс дат и окончания подписки использует этот часовой пояс. `CORS_ORIGINS` должен включать точный origin frontend, например `http://localhost:3000` (и `http://127.0.0.1:3000`, если используете этот адрес). Остальные настройки worker/LLM — по серверной инструкции. Не включайте local fallback с внешним PostgreSQL.
4. Создайте обычную учётную запись владельца в **том же** Supabase Auth, подтвердите email, скопируйте Auth UUID. Назначьте первого администратора доверенной CLI:

   ```sh
   cd backend
   export ENVIRONMENT=staging
   export INITIAL_ADMIN_EMAIL='owner@your-domain.kz'
   # DATABASE_URL и SUPABASE_* уже заданы в защищённом окружении backend.
   .venv/bin/python -m app.bootstrap_admin --user-id '<Supabase Auth UUID владельца>'
   unset INITIAL_ADMIN_EMAIL
   ```

   CLI сверяет подтверждённый email через Supabase Admin Auth API. Она не заменяет существующего администратора. Далее назначение ролей выполняется через админ-панель. Удалите INITIAL_ADMIN_EMAIL также из постоянного окружения после bootstrap.
5. В `frontend/.env.local` задайте **только публичные** параметры:

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=https://<staging-project-ref>.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=<публичный anon key этого проекта>
   NEXT_PUBLIC_API_URL=http://localhost:8000
   ```

   API URL — origin backend без `/api` и без завершающего `/`: клиент сам добавляет `/api/admin/...`. Service-role, DATABASE_URL, JWT secret и INITIAL_ADMIN_EMAIL в frontend не передаются. NEXT_PUBLIC-переменные фиксируются при сборке; после изменения пересоберите клиент.
6. Запустите обновлённый backend и frontend. Например, из backend с настроенным окружением: `.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000`. В другом терминале:

   ```sh
   cd frontend
   npm ci
   npm run typecheck
   npm run build
   npm start
   ```

7. Откройте `http://localhost:3000/admin`, введите email и пароль Supabase Auth. У администратора появятся четыре вкладки. У teacher/methodist — сообщение об отсутствии прав и выход под другим аккаунтом. В рабочем пространстве `/` ссылка находится в окне профиля. Проверьте продление, блокировку, лимит и запись аудита на отдельных staging-пользователях.

## Поведение и контракты

- Вход через `supabase.auth.signInWithPassword`; текущий access token передаётся как Bearer. Роль проверяется через `/api/admin/me`, а не metadata/JWT роль браузера. Проверка повторяется при фокусе и раз в минуту. При любом admin API 401/403 данные и диалог скрываются; backend проверяет права на каждом запросе.
- Четыре вкладки: аналитика с периодами и графиком; пользователи с серверными поиском/фильтрами/пагинацией; организации и добавление; лента генераций и серверный аудит. Нет демонстрационных данных или успешного fallback при недоступном API.
- Сохранение пользователя отправляет только изменённые поля, включая явный null для снятия срока/колледжа. Причина обязательна в UI. Последнего администратора защищает backend (409). Сбросить возвращает исходную дату в форме; «Бессрочно» отправляет null. +30/+90 дней продлевают от более позднего из текущего момента и существующего срока. Выбранная вручную дата означает конец суток Asia/Almaty. Продление само по себе не снимает блокировку.
- Лимит считает реальные LLM-вызовы, включая ошибки; комплект может потребовать несколько вызовов. Среднее время — реальное duration_ms завершённых вызовов. При отсутствии usage выводится «Нет данных», а не фиктивное число токенов.
- «Всего преподавателей» и counts колледжей — текущие teacher+methodist, без admin. Активные за 24ч/7д — пользователи с authenticated API обращениями. Период применяется к генерациям, а не к текущему составу пользователей. Колледж события берётся на момент генерации. Длинный график объединяет суммы в интервалы, сохраняя итоги.
- Ошибки загрузки, пустые выборки, ожидание, отсутствие настройки Auth и ошибки сохранения показываются явно. Диалог поддерживает клавиатуру/Escape и удержание фокуса; таблицы прокручиваются внутри карточек на узком экране.

Для недостающих UI-данных добавлены обратно совместимые read-контракты backend: `/profile/access` (только собственный профиль), `/api/admin/me`, `/api/admin/audit?limit=100&offset=0`; флаг `all_time` аналитики, `average_duration_ms`, `total_teachers`, `by_organization[].teachers`, `organizations[].teachers_count`, фильтр users `is_active`, подписи пользователя/колледжа в logs. Изменений SQL для этих дополнений нет. Backend и frontend нужно выпускать совместно.

## Проверки

```sh
cd frontend
npm run typecheck
npm run build
npx playwright install chromium
npx playwright test --config=playwright.admin.config.ts
```

E2E-конфигурация сама запускает отдельный frontend на 127.0.0.1:3102 с синтетическими публичными credentials и отдельным build-dir; существующий сервер на этом порту не переиспользуется. Auth/API ответы перехватываются только в браузерных тестах. При необходимости `E2E_CHROMIUM_PATH` задаёт путь к уже установленному Chromium. Эти тесты не подтверждают подключение к реальному Supabase.

Результат: **7 браузерных сценариев успешно**, **67 серверных тестов успешно** (включая 14 проверок нативного PostgreSQL). TypeScript и production build прошли.

Проверены: неверный пароль; отказ teacher; отсутствие admin-ссылки у teacher; Bearer во всех административных запросах; фильтры и сохранение доступа/лимита; дата подписки и снятие привязки колледжа; добавление колледжа; настоящий формат audit details.field/before/after; ошибки API и повтор; скрытие данных при отзыве роли; выход; мобильная ширина 390px и Escape; прежняя навигация рабочего пространства. Скриншоты `docs/admin-ui/` содержат исключительно синтетические данные.

Серверные регрессии запускаются на одноразовом PostgreSQL локально: `PG_BIN=/Library/PostgreSQL/18/bin bash backend/scripts/test_postgres.sh -q`. Новые контракты проверены на изолированной SQLite fixture; существующие RLS/permissions/изоляция/квоты дополнительно покрыты PostgreSQL-набором. XML-результаты находятся в `docs/backend-admin-test-results.xml` и `docs/frontend-admin-test-results.xml`.

Установленный Next.js 16.4.3 выводит предупреждение об известной уязвимости; первая команда сборки была остановлена им, повторная завершилась успешно. До deployment требуется отдельное обновление безопасности и повторная проверка. Зависимости в этом этапе не обновлялись. Реальный staging Auth, CORS, runtime DB permissions, CLI bootstrap и проверки с реальными аккаунтами остаются владельцу после подключения.
