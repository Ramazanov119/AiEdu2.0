# Единый SQL для существующего legacy Supabase

Файл: `supabase/migrations/20261123999999_full_sync_production.sql`. Это ручная альтернатива миграциям 00001–00005 для SQL Editor, а не дополнительный последовательный шаг после повторного применения этих файлов. Скрипт также допускает запуск поверх уже применённых миграций и повторный запуск самого себя.

Сделайте backup и проверьте на staging-копии. В Supabase SQL Editor выберите нужный проект, запустите **всё содержимое файла** от BEGIN до COMMIT от имени владельца миграций. При ошибке транзакция целиком откатывается; в сессии с незавершённой ошибочной транзакцией сначала выполните ROLLBACK. lock_timeout=5s позволяет прекратить ожидание блокировки вместо долгого удержания DDL. Запуск на рабочей базе в этой задаче не выполнялся.

Что сохраняется:

- Все существующие profiles UUID и данные full_name/college/status/plan. NOT NULL снимается только с full_name/college. Если institution пустой, туда переносится существующее отображаемое название college; организации по названию не создаются и не назначаются.
- Существующие role/is_active/subscription_until/daily_limit не сбрасываются при повторном запуске. Для впервые добавляемых полей используются defaults teacher/true/NULL/20. Старые status/plan **не интерпретируются**: перед включением нового backend владелец должен явно перенести блокировки и сроки доступа старой системы. Нельзя считать прежний status='blocked' автоматически перенесённым в is_active=false.
- Создаются все таблицы предыдущих миграций и админки, включая generation_reservations для конкурентного резервирования квот. Auth-профили синхронизируются по UUID; подтверждённый Auth email обновляет email, без назначения роли admin.

Границы изменения безопасности:

- На перечисленных таблицах AiEdu заменяются **все** прежние public RLS policies и клиентские grants: чтение только собственных записей, прямое редактирование профиля только full_name/institution. Старый клиент, который напрямую пишет status/plan/college, задачи или пути файлов, после этого потребует серверного API. Это осознанное закрытие прежнего FOR ALL доступа; код рабочего приложения скрипт не меняет.
- Серверная NOLOGIN-группа aiedu_backend создаётся только при отсутствии. Владелец отдельно выдаёт `GRANT aiedu_backend TO <server_runtime_login>`; браузерным ролям эта группа не выдаётся. Runtime login не должен владеть таблицами, иметь SUPERUSER/BYPASSRLS или DDL. Service-role credentials остаются на сервере.
- agent_audit/generation_logs/admin_audit_logs защищены от UPDATE/DELETE/TRUNCATE grants и триггерами. Пользователь не может повысить роль или изменить системные поля прямым Supabase UPDATE.
- Только bucket portfolio-private получает owner SELECT/INSERT/DELETE и restrictive guards для anon/authenticated. Сторонние storage policies не удаляются, а guards не меняют доступ к другим bucket. Уже существующий публичный portfolio-private вызывает отказ всей транзакции: его публичность нужно отдельно проверить и исправить владельцу.

Скрипт рассчитан на profiles.id UUID PRIMARY KEY, совместимые UUID-ключи связанных бизнес-таблиц и стандартные Supabase auth/storage. Для каждой из семи бизнес-таблиц (portfolio_files/tasks/task_steps/lessons/lesson_materials/chat_messages/agent_audit) сразу после CREATE TABLE IF NOT EXISTS перечислены ADD COLUMN IF NOT EXISTS для всех колонок, до любых индексов и owner RLS. В существующей таблице недостающие бизнес-значения остаются NULL; применяются только технические defaults (идентификатор, timestamp, pending, false, пустые JSON-контейнеры). Пустые пути файлов, фиктивные результаты и связи не выдумываются.

Если user_id существует, UUID копируется в owner_id только при owner_id IS NULL. Текстовые канонические UUID также поддержаны; невалидные/другие внешние идентификаторы не преобразуются, старые строки сохраняются с NULL owner_id и недоступны через owner RLS до явного сопоставления. Уже назначенный owner не перезаписывается. Все обычные legacy-колонки вне новой схемы, включая user_id, сохраняют свои данные, но становятся nullable, чтобы новые вставки не требовали дублирования старых полей.

Первичные ключи/identity не удаляются и не перестраиваются: PostgreSQL требует для них NOT NULL. Автоматически заполняемые старые ключи сохраняются; старый PK вне новой схемы без default вызывает понятный атомарный отказ, поскольку без явного сопоставления ключей безопасно разрешить вставки нельзя. Существующие типы колонок, уникальные/check/FK constraints и сторонние triggers также автоматически не переписываются. Поэтому выполнение поверх произвольной неизвестной схемы гарантировать нельзя. Для profiles по-прежнему снимаются только full_name/college NOT NULL: иные обязательные profile-колонки без default вызывают явный отказ до установки Auth trigger, а не угадывание status/plan.

На время миграционного переноса владельца agent_audit известный UPDATE/DELETE trigger неизменяемости заменяется под удерживаемой до COMMIT эксклюзивной DDL-блокировкой; в конце он обязательно восстанавливается. Неизвестные триггеры не отключаются. Права на sequence выдаются по фактическому pg_get_serial_sequence, а не по предполагаемому имени: существующий UUID id не требует agent_audit_id_seq.

Проверка: **97 серверных тестов успешно**, включая 30 проверок полного скрипта на отдельном одноразовом локальном PostgreSQL. Пять исходных схем: legacy profiles, empty, previous_migrations, семь существующих legacy-таблиц с UUID user_id и с текстовым user_id. Проверены новые вставки во все семь таблиц от серверной роли без legacy-полей, сохранение прежнего owner и необрабатываемых внешних IDs, nullable legacy user_id/legacy_required, существующий UUID agent_audit.id и ранее установленный immutable trigger, повторное выполнение, сохранность данных и прав, новые Auth пользователи без full_name/college, RLS/запрет повышения роли, неизменяемость логов, storage isolation при посторонней permissive policy и атомарный отказ для публичного bucket. Тесты — `backend/app/tests/test_full_sync_migration.py`, результаты — `docs/full-sync-test-results.xml`.

```sh
PG_BIN=/Library/PostgreSQL/18/bin bash backend/scripts/test_postgres.sh -q
```

Эта команда создаёт и удаляет только собственный временный локальный кластер и не использует рабочий DATABASE_URL. Нативные тесты эмулируют Supabase schemas; подключение к реальному Supabase, возможности production SQL Editor и сторонние Auth triggers не проверялись.
